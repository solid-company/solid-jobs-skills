# solid-jobs-skills

An AI job-search command center for the [SOLID.Jobs](https://solid.jobs) public API.
A Go binary (`sjctl`) does the deterministic work — fetching offers, caching, tracking, stats —
and Claude skills add the judgment layer (search-from-language, offer evaluation,
digests).

## Architecture

```
cmd/sjctl              CLI (cobra) — thin wrapper, no business logic
internal/api           SOLID.Jobs API client (typed models, campaign param, 429 backoff)
internal/store         SQLite store — typed wrappers over the generated queries
internal/store/schema.sql   table definitions (sqlc source + runtime DDL)
internal/store/query.sql    all SQL queries (sqlc source)
internal/store/sqlcgen      GENERATED by sqlc — do not edit by hand
internal/jobs          Service layer — ALL business logic lives here
internal/stats         Salary/market aggregation
.claude/skills         jobs-search, jobs-create-profile, jobs-evaluate, jobs-track, jobs-digest
config/                profile.md template
data/                  solidjobs.db (gitignored)
```

**Dependency rule:** `cmd/sjctl` and any future dashboard depend on `internal/jobs`,
never the reverse. Put logic in the service layer, not in commands. SQLite is the
single source of truth for offers, profiles, tracker, evaluations and watches.

**SQL rule:** no SQL is inlined in Go. All queries live in `internal/store/query.sql`
and the schema in `internal/store/schema.sql`; [sqlc](https://sqlc.dev) compiles them
into the typed `sqlcgen` package. The `store` package wraps those generated methods.
To change the database layer: edit the `.sql` files, run `sqlc generate`, then update
the wrappers in `internal/store/*.go`.

## Build & run

```
sqlc generate                     # regenerate internal/store/sqlcgen after editing *.sql
go build -o sjctl ./cmd/sjctl     # build the binary (sjctl.exe on Windows)
go test ./...                      # run tests
./sjctl search -d IT --term golang --remote --json
```

Install the sqlc tool once with `go install github.com/sqlc-dev/sqlc/cmd/sqlc@latest`.
sqlc is a build-time tool only — it is not a runtime dependency in `go.mod`.

Skills resolve `sjctl` in order: on `PATH` → `~/.solid-jobs-skills/bin/sjctl`
(installer location) → `./sjctl` in the repo → install via the bootstrap script
→ `go run ./cmd/sjctl` (dev fallback).

## Distribution

The skills ship via [skills.sh](https://skills.sh) (`npx skills add
solid-company/solid-jobs-skills`), which copies only the `.claude/skills/*`
folders — not the Go source. So the binary is delivered separately:

- **Releases:** `.goreleaser.yaml` + `.github/workflows/release.yml` build a
  cross-platform matrix (linux/darwin/windows × amd64/arm64) on every `v*` tag.
  Pure-Go SQLite means `CGO_ENABLED=0` and clean cross-compilation. Each archive
  is named `sjctl_<os>_<arch>.{tar.gz,zip}` with a `checksums.txt`.
- **Bootstrap:** `scripts/install-sjctl.{sh,ps1}` detect OS/arch, download the
  matching release asset, verify its sha256, and install to
  `~/.solid-jobs-skills/bin`. Idempotent (skips if version matches). Skills curl
  these from raw GitHub when `sjctl` is absent.
- **Signing:** GoReleaser signs `checksums.txt` with keyless **cosign** (Sigstore
  OIDC, no stored key); the cert binds the signature to the release workflow.
  Both installers verify `checksums.txt.{sig,pem}` when cosign is on PATH before
  trusting the checksums (`SJCTL_SKIP_COSIGN=1` to bypass). The release workflow
  needs `id-token: write` for OIDC.
- **Version:** `main.version` is stamped via `-ldflags "-X main.version=..."`;
  `sjctl version` prints it, and the installer uses it to skip re-downloads.
- **Self-update:** once installed, `sjctl` keeps itself current without re-running
  the bootstrap. A daily-cached check (`cmd/sjctl/update.go`) resolves the latest
  release, downloads the os/arch archive, verifies the keyless **cosign**
  signature over `checksums.txt` and then the archive's sha256 against it, and
  atomically swaps the running binary (effective next run) — the same trust chain
  the installer uses, since first-install cosign does not cover later updates.
  Runs on every command via the root `PersistentPreRun` (skips `version`/`update`/
  `help`); `sjctl update [--force]` triggers it on demand. The cosign-absent
  policy differs by path: the explicit `sjctl update` warns and proceeds (user is
  present), but the unattended auto-update **aborts** rather than install
  unverified code; `SJCTL_SKIP_COSIGN=1` bypasses both. The auto-updater is pinned
  to the canonical repo and ignores `SJCTL_REPO` (honored only by explicit
  `update`). `dev` builds never self-update; `SJCTL_NO_AUTO_UPDATE=1` disables the
  auto-check. This is why a new tag reaches existing users without a manual
  reinstall — the skill's `curl|bash` bootstrap only fires when the binary is
  missing. The bootstrap script URL in the skills is pinned to a release tag (not
  `main`) so it is immutable.
- **DB location:** `defaultDBPath()` resolves `SJCTL_DB` → `~/.solid-jobs-skills/solidjobs.db`,
  so the binary works from any working directory once installed.

To cut a release: tag `vX.Y.Z` and push; the workflow runs GoReleaser. Test
locally with `goreleaser release --snapshot --clean`. The pinned bootstrap URL is
a maintenance tripwire — the tag it points at must exist and contain
`scripts/install-sjctl.{sh,ps1}` or all five skills 404 on first install, and the
pin must be bumped in every skill on each release or it goes stale (the script
still resolves "latest" for the binary, but it is fetched from the pinned tag).
Release checklist: after tagging, bump the `.../<tag>/scripts/install-sjctl.*`
URLs in all five `.claude/skills/*/SKILL.md` to the new tag.

## sjctl command map

| Command | Purpose |
|---------|---------|
| `search` | Query the live API, cache offers, print table/JSON |
| `track add/list/set/note/rm` | Application pipeline (saved→applied→interview→offer/rejected; auto-expire) |
| `evaluate save/show` | Persist/read AI evaluations (grade + dimensions + rationale) |
| `profile add/list/show/import/set-default` | Manage CV/preference profiles |
| `watch add/list/rm` | Saved searches for sync |
| `sync` | Run watches, report offers not seen before |
| `stats` | Salary min/median/max, remote share, counts over cached offers |
| `update` | Self-update to the latest release (verified); runs automatically once/day |

Global flags: `--db`, `--campaign`, `--json`, `--profile`.

## Skill routing

- "find / browse jobs" → **jobs-search**
- "set up / update / switch my profile, here's my CV" → **jobs-create-profile**
- "is this worth it / evaluate this offer" → **jobs-evaluate**
- "track / I applied / my pipeline" → **jobs-track**
- "what's new / digest" → **jobs-digest**

## API facts

- `GET https://solid.jobs/public-api/offers/{division}`; divisions are case-sensitive
  (IT, Engineering, Marketing, Sales, HR, Logistics, Finances, Other).
- No auth — only a mandatory `campaign` param (lowercase/digits/hyphens, ≤64 chars);
  default `solid-jobs-skills`.
- Rate limit 300 req/min per IP; the client retries 429 with exponential backoff.
